# Page SEO and social images

The seven main pages and every service get a static 1200 × 630 PNG social image.
Images are generated by `npm run build`. No screenshot step, external image API,
or request-time image server is needed.

## Preview the cards locally

```sh
npm run start
```

Open `http://localhost:4321/dev/og/`, or use the port printed by Astro.
The gallery includes the seven main pages, all services, and the sitewide default.
Click a card to open or save its full-size PNG. The preview has `noindex, follow`
and is not generated or included in the sitemap in a production build. The PNGs
are public in production so social crawlers can fetch them.

To check production output:

```sh
npm run build
npm run check:seo
```

The check inspects the generated HTML and PNG files for distinct descriptions and
image URLs, matching social tags, image dimensions, and preview exclusion.
It does not contact Google or social platforms.

## Edit a main page in Decap

Open `/admin`, then **Site Settings → SEO Settings**. Choose Home, About, Services,
Contact, Direct Billing, Gallery, or Reviews.

- **SEO Title** is the page-specific title. Do not add `| Glow and Relax`.
  The layout adds the current business name once. The same page-specific title
  supplies Open Graph and Twitter titles.
- **SEO Description** supplies search and social descriptions. Write a unique,
  factual summary. About 130–160 characters is a useful guide, not a limit.
  Search engines can choose a different snippet.
- **Generated Card Photo** changes the photo used in the automatic card.
  It does not change the photo on the visible website page.
- **Complete Social Image Override** replaces the entire card with your own artwork. Leave it empty
  for automatic generation. Upload JPG or PNG, ideally 1200 × 630.
- **Social Image Alt Text** describes the resulting social image. Update it if you
  change the photo or upload different artwork.

A blank title or description uses the global value. A blank photo uses the
configured global photo, then the built-in clean homepage photo. An empty page
social image override uses that page's generated card, not the global image override. The
global social image override controls the default card used by other routes.

## Edit or create a service in Decap

Use **Services** and fill in the usual service content and photo. Its page and
social card are generated automatically; no extra map or image upload is needed.
The service title and photo supply the card. Changing its card description does
not have to change its SEO description.

The optional collapsed **SEO** section has independent overrides:

- **SEO Title** changes head metadata without changing the H1 or service name.
  If empty, the title is the service name followed by the configured city and
  province. The layout adds the business name once.
- **SEO Description** changes metadata without changing visible card or hero
  copy. If empty, the main service description is used, then the short card
  description, then the global description. Review this fallback when adding
  a service; it can be longer than a search snippet.
- **Complete Social Image Override** is a complete custom card. Leave it empty for the branded card
  generated from the service photo.
- **Social Image Alt Text** describes a custom uploaded card. Generated cards have
  a service-specific default.

Existing service SEO descriptions have been written individually. Clearing an
optional field, or leaving the entire SEO section absent, is supported.

## Custom image sizing

All outputs are PNG at 1200 × 630 pixels. A custom complete card is fitted inside
that size with a warm cream background, rather than cropped. This preserves text
on artwork with a different aspect ratio. A correctly sized source avoids any
padding. Automatic card photos are cropped to their photo panel.

The generated main-page cards use different existing illustrative photos.
Stock photographs are not presented as verified staff portraits or clinic
exteriors. The global default shares the homepage photo.

## Publishing and cached previews

1. Save or publish the edit in Decap. Decap commits to the configured `main` branch.
2. Let the normal Git-connected host run `npm run build` and publish `dist`.
3. Confirm that deployment completed before testing the public URL.
4. Rescan the page in opengraph.xyz or a platform's sharing inspector.

The build generates both the page and image together. Image URLs include a hash
of their inputs. A photo, visible card text, logo, or font change gives the card
a new URL. Platforms can still cache the old page metadata, so a rescan may be
needed. The repository does not configure the host's Git deployment settings;
its existing automatic deployment must remain enabled. No production deployment
was performed as part of this implementation.

## Developer files

- `src/data/seo-pages.json`: main-page metadata, source photos and overrides.
- `src/content/services/*.md`: service content and optional SEO data.
- `public/admin/config.yml`: corresponding Decap controls.
- `src/content.config.ts`: blank-safe service SEO validation.
- `src/lib/seo.ts`: fallback rules, card copy, image descriptors and hashed URLs.
- `src/lib/og-image.tsx`: shared Satori layout and Sharp PNG renderer.
- `src/pages/og/[card].png.ts`: static image output.
- `src/pages/dev/[preview].astro`: development-only preview gallery.
- `scripts/check-seo.mjs`: production-output checks.

Card headlines, action lines, and layout are developer-controlled in the two
library files. They are separate from search metadata so a title edit does not
unexpectedly change the artwork. Increment `TEMPLATE_VERSION` in `seo.ts` after
changing the visual template to refresh card URLs. Satori is the one new runtime
package used only during the static build. The regular Mona Sans WOFF used by the
renderer is stored locally; its source and SIL OFL license are documented in
`public/fonts/README.md` and `public/fonts/MonaSans-OFL.txt`.
A narrow npm override uses `fflate` 0.7.5 inside Satori to avoid its pinned
0.7.3 malformed-ZIP advisory. Other existing dependency advisories are outside
this metadata change.

The build reads source assets from the project root and never requests photos
from the deployed site. Run commands from the repository root. Standard Astro
builds and the existing `npm run build` script already do this.
